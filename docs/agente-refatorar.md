# Polish Agent (`/refatorar`)

The Refactoring Agent is the golden closure of the project's coding flow. Its performance is vital to ensure the codebase's scalability and avoid "software rot".

---

## 1. The Agent's Focus

When the developer runs their test suite (Green Phase) and confirms that the expected behavior is delivered perfectly, the Refactoring Agent is triggered.

Its central focus is aesthetic, structural, and architectural, primarily aimed at improving what was built by the Code Agent:
* **Iterative Update Rule (`task.md`):** It analyzes the code and maps all refactoring targets in a task list, handling **one target at a time** (e.g., extracting a single method, then marking it `[x]`), eliminating cognitive overload.
* **Elimination of God Classes:** The model is trained to detect if the main class absorbed too much logic while simply trying to "make the test pass". It will actively act to break the logic into smaller classes.
* **SOLID Principles:** Actively scanning and ensuring the Single Responsibility Principle (SRP), Open/Closed (OCP), Dependency Inversion (DIP), among other bases that bring superior readability.
* **Redundancies and "Code Smells":** Eliminate unnecessary boilerplate, deep nesting (flattening conditionals via early returns), and replacing magic numbers with named constants.

---

## 2. The Absolute Behavioral Restriction

A cardinal rule locks the AI at this point: **Do not add features and do not change behavior.**

At this moment, the application's business rules have been consolidated in the Artifacts, validated by the Red Phase, and materialized in the Green Phase. Since refactoring seeks only structural gain, trying to "invent" or "improve" the system's behavior would break the entire architectural alignment of the project. 

All changes made to methods, instance injections, or class variables have only one goal: to create readability and maintainability without changing a single bit of the tested function's external behavior. The agent relies heavily on ensuring the tests continue to pass; therefore, refactoring without existing test coverage is strictly forbidden.

**Bash Constraints:** Terminal commands (like `pytest`) are provided strictly inside single, isolated bash blocks for manual user execution. Autonomous execution is disabled.

---

## 3. The Context in the TDD Flow

Its role is the final quality seal:
1. Works with its hands tied, ensuring results only on top of the logic generated by the **Code and Tests Agents**.
2. As a mandatory final step that does not deal with algorithms that "do not yet exist", the AI can focus all the processing of its token window purely on architectural reading.
3. Once its flow is finished, the project reaches commercial stability and the cycle concludes with the application of safe refactoring (because the green suite guarantees that nothing was actually broken).
4. After refactoring, it proactively advises the user to start a **new chat session** for the Audit (`/review`) phases, resetting the token window and ensuring maximum QA accuracy.
