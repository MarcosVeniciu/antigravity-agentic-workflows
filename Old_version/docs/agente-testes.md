# Tests Agent (`/testes`) - The Red Phase

The Tests Agent is the starting point of the development cycle after the architecture has been approved. Strictly following the TDD (Test-Driven Development) philosophy, it acts in the **Red Phase**, that is, it creates the tests before any line of production logic exists.

---

## 1. The Agent's Focus

The central goal of this agent is to create a protective mesh for the next step (coding). It takes the technical document (SDD) generated by the Artifacts agent — which has already defined classes, methods, and contracts — and transforms it into executable assertions.

### AAA Pattern (Arrange-Act-Assert)
All tests generated by this agent strictly follow the AAA pattern:
1. **Arrange:** Configuration of the initial state, mocks at the boundary level, and fixtures.
2. **Act:** Execution of the target function or method.
3. **Assert:** Validation of results and expected state changes.

### Comprehensive Coverage (The 4 Categories)
The generated test suite is divided into fundamental pillars:
* **Happy Path:** The nominal flow with valid inputs, based on the original BDD contract.
* **Edge Cases:** Limiting cases, boundary values, empty inputs, and maximum limits.
* **Exception Paths:** Rigorous validation that the code fails with expected exceptions when subjected to invalid inputs, external service outages, or invalid data types.
* **Performance / Native Profiling:** Tests focused on measuring response times iteratively (e.g., N=10, 100, 1000). Uses native tools like `time.perf_counter()` to output a tabular mini-report to `stdout`. This prepares the ground for asymptotic complexity analysis (Big-O) later audited by `/review performance`.

---

## 2. Strict Constraints (Stubbing & No Logic)

**Forbidden to generate production logic:** The Tests Agent is absolutely forbidden to implement business logic. 
However, it **MUST create empty signatures (Stubs)** for methods, classes, and functions (e.g., `def func(A, B): pass`) in the corresponding production files if they don't exist yet. This ensures the tests can be imported without syntax errors during the Green cycle.

It is also strictly forbidden to execute terminal commands itself. It only provides isolated `bash` blocks with the exact test execution command (e.g., `pytest -s -v`) for the user to run.

---

## 3. The Context in the TDD Flow

This agent does not act in isolation. The development flow heavily depends on what it produces:
1. It receives the contracts from the **Artifacts Agent** (`/artefatos`).
2. It generates the failing tests (Red Phase) and necessary stubs.
3. Once the test suite is created, it passes the baton to the **Code Agent** (`/codigo`), whose exclusive mission will be to make that suite pass (Green Phase).

Having an agent that focuses 100% only on structuring tests prevents the model from trying to write the validation and the implementation simultaneously, which would frequently result in biased tests (tests created just to pass on the specific logic that the AI just came up with).


---

## 🔀 Dynamic State Machine Router

This agent is built using the **State Machine Router (Dynamic Context)** architecture. To prevent prompt hallucination, the trigger in `workflows/testes.md` is purely a lightweight router.

When invoked, the agent dynamically fetches its heavy execution instructions from the Obsidian Vault (`08-templates-and-workflows/`) using the MCP:
- `workflow-testes-EXECUTION.md`
