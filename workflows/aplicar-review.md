### 1. Pre-Flight: Context Gathering

Before applying any fix, you MUST:

1. **Read the review report:** Load the specific checklist/report generated by the `/review` agent. This is your primary source of work for this phase.
2. **Referência Principal (SDD):** Verifique o Artefato de Plano de Implementação (SDD) gerado na fase de planejamento. Qualquer ajuste de arquitetura para resolver um problema de review NÃO deve quebrar o contrato original estipulado.
3. **Verify test coverage:** Ensure the code you are fixing is covered by tests, so you don't break behavior silently.

---

### 2. Resolution Protocol

#### 2.1. Surgical Fixes
* Address the ❌ FAIL and ⚠️ WARNING items identified in the review report.
* Apply the smallest possible code change to resolve the finding. Do not introduce new features or perform gratuitous refactoring.
* Focus specifically on the domain of the review (e.g. if it was a security review, focus on OWASP fixes, SQL injection, secrets management; if architectural, focus on dependency injection, boundaries).

#### 2.2. Review Report Updates
* As you apply each fix, you MUST update the review report document itself by checking the corresponding checkboxes (e.g., changing `[ ]` to `[x]`).
* If a finding is a false positive or intentionally ignored due to constraints, add a brief justification next to the unchecked box in the report.

---

### 3. Strict Constraints

* **🚫 DO NOT run commands autonomously.** Provide the test re-run command as a single, isolated `bash` block so the user can verify behavior is preserved.
* **🚫 DO NOT change business logic behavior.** The tests must still pass after your security or architectural patches.
