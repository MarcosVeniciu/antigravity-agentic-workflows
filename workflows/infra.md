---

### 1. Pre-Flight: Context Gathering

Before making any infrastructure change, you MUST:

1. **Read the vault:** Query `07-environment-setup/` in the `obsidian_knowledge_graph` MCP vault to understand the current environment configuration, Docker setup, and dependency management strategy.
2. **Read conventions:** Query `02-conventions/` for any rules on package management, version pinning, or container standards.
3. **Verify the artifacts:** Review the implementation plan generated by `/artefatos` to identify exactly which new dependencies, services, or environment variables are required.

---

### 2. Dependency Management Protocol

#### 2.1. Package Analysis

For each new dependency required:
* **Justify:** Explain why this package is needed (what problem it solves that can't be solved with existing dependencies).
* **Version Strategy:** Specify the version with appropriate pinning (exact for production, range for dev dependencies).
* **License Check:** Flag any dependency with a license incompatible with the project (GPL in an MIT project, etc.).
* **Size Impact:** Note if the package is unusually large or pulls in many transitive dependencies.

#### 2.2. File Updates

Identify and update the relevant dependency files:
* `requirements.txt`, `pyproject.toml`, `Pipfile` (Python)
* `package.json` (Node.js)
* `go.mod` (Go)
* Or any other project-specific dependency manifest.

---

### 3. Container & Environment Protocol

#### 3.1. Dockerfile Changes

If the feature requires Dockerfile modifications:
* Follow multi-stage build practices to keep image size minimal.
* Document any new `ENV` variables with comments explaining their purpose.
* Ensure build cache efficiency (order layers from least-changing to most-changing).

#### 3.2. Docker Compose / Orchestration

If new services are introduced (databases, caches, message brokers):
* Add the service definition to `docker-compose.yml`.
* Define health checks for new services.
* Map volumes and ports explicitly.

#### 3.3. Environment Variables

For each new environment variable:
* Add it to `.env.example` with a descriptive placeholder value.
* Document its purpose, expected format, and whether it is required or optional.
* **NEVER** commit actual secrets — only placeholder values.

---

### 4. Output Rules

* **Show install commands** as individual, copy-pasteable `bash` blocks. One command per block.
* **Do not run commands.** The user will execute them manually.
* **Show a diff summary** of all files changed (dependency files, Dockerfiles, .env.example).
* **🚫 DO NOT combine terminal commands.** Each command MUST be in its own separate, isolated bash code block. Do not put multiple commands in the same block, and do not chain them with && or ;. This allows the user to copy each command individually.
